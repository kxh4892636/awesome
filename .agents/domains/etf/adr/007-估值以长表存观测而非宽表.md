# 007-估值以长表存观测而非宽表

估值初稿是宽表 `(symbol, data_date, pe, pb, ps, dividend_yield)`。实现时改成主键为 `(symbol, metric, trade_date)` 的长表：

```sql
security_valuation(symbol, metric, trade_date, value, percentile, updated_at)
PRIMARY KEY(symbol, metric, trade_date)
```

理由是四指标的到达相互独立（上游按 `valuationType` 逐个请求）。宽表要么用 NULL 占位，把「上游还没给」和「根本算不出」混成一种状态；要么每加一个指标就改表。长表里「有行 = 有这个观测」，缺指标就是没有行，加指标不改表结构，取序列只多一个 `metric` 等值条件。分位逐行存，因为分位随历史增长而变，不能事后重算。

Considered Options：宽表 + NULL（语义混淆、加指标要迁移）；宽表 + JSON 列（查询与索引代价高，Drizzle 类型也退化）；每指标一张表（四张表四种迁移与四份 repository 代码，收益只有列名更短）。

Consequences：行数约 3 倍（930955.CSI 四指标 9200 行，五只证券库内合计 20876 行，2026-11-17 实测），SQLite 上可忽略；序列查询与回填 upsert 都要带 `metric` 条件，漏掉就会跨指标合并；主键三元组让重复回填天然幂等。

> 补充（2026-11-23，seq 1131..1139）：表上只有复合主键的隐式索引（列序即 `(symbol, metric, trade_date)`），没有二级索引、没有外键、没有 CHECK，`metric` 的枚举只在 TypeScript 层校验（SQL 里是裸 `text`）。所以新增指标不改表、不需迁移，但库里允许任意 `metric` 文本，读侧一律按 `valuationMetrics` 白名单取，别裸查 `WHERE symbol=?`。
