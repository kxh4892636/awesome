# 015-轮转不扣用户 prompt RPC

## 背景

轮转曾把用户那条 prompt RPC 扣住，等「检查点轮 → 压缩 → 恢复轮」跑完才放行（40 秒到数分钟）。两次真机故障都源于这个窗口：

- 2026-11-20 49a3964c：等待期间客户端切走会话，RPC 的 `AbortSignal` 被 abort。轮转一度复用它，于是压缩被跳过、恢复轮注入抛错、用户消息从未入库，只留 stderr 的 warn（看不到）。修法一：轮转内部改用独立 `detached` 信号。
- 同一窗口的第二个后果：客户端只在「宿主受理」时清空输入框。受理迟到且客户端已切走，草稿从 `localStorage` 还原；消息被 `detached` 放行后，界面出现「已发送但文本还在」。修法二：受理提前。

## 决策

命中轮转时 `prompt` **立刻**返回 `{ accepted: true }`，四步放进后台异步函数（`void` 启动、自带 try/catch/finally），最后一步仍是 `original(request, detached)` 放行用户消息。轮转内部的等待、压缩与放行一律用 `detached` 信号，调用方断连不再参与。

## 后果

- 输入框在受理那一刻清空，切走/刷新不再残留已发送文本；客户端断连也不打断压缩。
- 受理早于入队：宿主在后台链路中途崩溃会丢这条消息（与改动前「客户端放弃即丢」同一量级，未新增风险面）。
- 输入框立即解锁，用户在轮转几十秒内再发一条会先开下一轮，压缩撞 `busy` 被跳过（只 warn）。
- `rotating` 的清理移到后台链路的 finally，`rotatedAt` 仍按 `maxSeq` 落账。

## 备选与否决

- 改为 `turn/end` 后轮转、完全不碰用户 RPC：窗口彻底消失，但要重做触发与去重，且压缩会落在昂贵的那一轮之后，失去「先腾上下文再跑消息」的意义。
- 改宿主客户端（迟到的受理也清空草稿）：根因在客户端，但那是 npx 安装的上游包，改动不持久。
