# 003-轮转期间立即受理用户消息

## 背景

修好断连后，用户反馈：轮转期间切走会话再回来，消息确实发出去了，但输入框里的文本还在。取证结论（turn 7）：

- 输入框只在「宿主受理」时清空（`commit-draft`）；轮转把受理推迟了 47 秒。
- 等待期间切走会话 → 输入框被拆 → 草稿（`localStorage: dsh.conversation.<id>`）在回来时被读回；受理证明到达时客户端已无主，不再清空。
- 消息仍被放行（`detached` 生效），所以症状是「发了但文本还在」。

## 交付

- `redirect` 进入轮转后**立刻**返回 `{ accepted: true }`，把检查点轮 → 压缩 → 恢复轮 → 放行放后台执行；后台链路保留 `detached` 与全部 try/catch，最后一步仍是 `original(request, detached)`。
- `rotate.test.ts` 适配：等待后台链路完成后再断言（既有流程断言不变），保留断连用例。

## 验收

- `vp check`、`vp test src` 全绿。
- 语义变化记录在案：受理早于入队；宿主在后台链路中途崩溃时这条消息会丢（与改动前「客户端放弃即丢」同量级）。

## 依据

- 失败现场见本 Plan 001/002；客户端链路见 turn 7 取证（`input/facade.ts`、`input/machine.ts`、`sessions/session.ts`）。
## 结果

- `redirect` 判定轮转后立刻返回 `{ accepted: true }`，四步链放进 `background()` 用 `void` 启动；`detached`、失败语义、`rotating`/`rotatedAt` 落账不变；放行失败新增 `rotation release failed` warn。
- 单测 22 条：新增「受理不等轮转」与「放行失败只 warn 不留未处理 rejection」；变异验证（改回 await 会让三条用例超时、catch 改成 rethrow 会触发 unhandledRejection）。
- `vp check` 与 `vp test src`（294 例）全绿。

## 已知副作用

- 命中轮转时 `accepted` 早于入队：宿主在后台链路中途崩溃会丢这条消息（与改动前同一量级）。
- 受理后输入框立即可编辑，用户在轮转几十秒内再发一条会走原样放行；若它先结束检查点轮并开新轮，压缩会撞 busy 被跳过。
