# 010-修复撤回墓碑导致的会话日志损坏

## 现象

打开会话 `session-e09f821c-673c-4a0f-9930-a688319f2250` 时报：

```text
历史加载失败：stored session "…" is corrupt: session "…": stored log is corrupt:
SessionFormatError: system/message does not match an open turn and step
```

日志文件本身没坏：3714 条 JSONL、seq 连续、zstd 帧完整。坏的是**语义**。

## 根因

- 撤回（0.5.57–0.5.58）的宿主半在 `turn/end` 之后追加一条空内容 `system/message` 墓碑（`git show 12e10a0^:src/host/undo/undo-turn.ts`），`data.turn/step` 借用被撤回消息的坐标：seq 2837=27/1、2881=28/1、2937=29/1。
- v4 关系校验把 `system/message` 归入 step 事件（`dsh-session-format-v3-to-v4/src/relationships.ts:8`）：数据里的 turn/step 必须等于**当前打开的** turn/step（同文件 85–89、269 行）。
- 写入时只过行级准入（`system-message.ts:37-41`：turn/step 是正整数即可），所以活体会话不报错；冷读时 `assertV4LifecycleRelationships` 顺序重放，到墓碑即整条历史判 corrupt。
- 三条墓碑都在各自回合的 `turn/end` 之后；撤回功能已在 0.5.60 整体移除（[008](008-移除撤回功能.md)），不会再产生新的同类日志。

## 修复

1. 把三条墓碑移到所属回合**最后一个 `step/end` 之前**（turn 27→step 1、turn 28→step 4、turn 29→step 6），`data.step` 改成实际步号，`message.id` 重算。
2. 按新位置重排 seq，同步 `surfaceOp.startSeq/endSeq`、`sourceEventSeqs`（仍用区间压缩）、`data.recall.boundary/end` 等引用。
3. zstd 容器保持两帧：第一帧只有 header 行（冷读硬要求），第二帧是全部事件行。
4. 不删任何消息、不删任何帧：被撤回的区间依然通过表面替换对模型不可见。

脚本 `.temp/repair-recall.mjs`，原件备份 `.temp/session-e09f.original.zstd`，离线校验器 `.temp/validate-session.mjs`（直接调用宿主自己的 `sessionFormatCatalog` + v4 关系校验）。

## 验收

| 项 | 结果 |
| --- | --- |
| 离线 v4 校验 | `OK events=3714` |
| 两帧可独立解压 | header 帧 229 字节 1 行；事件帧以换行结尾 |
| 表面折叠 | 修复前后 517 个表面节点一一对应（墓碑 seq 平移），被撤回区间仍不可见 |
| 人类转录 | append 起源的 825 个消息节点一致 |
| 影响面 | 全机 253 个会话扫描，只有这一个受影响 |

端到端（GUI 重新打开该会话）需要宿主重新读日志；宿主进程正跑着本会话，重启要用户许可，本轮没做。

## 已知限制

- 被撤回的区间在**界面转录**里会重新可见：当时靠客户端 `visibility:hidden` 隐藏，那份代码已随 008 删除。只有模型可见历史仍被遮蔽。
- 墓碑现在落在已结束回合的最后一个 step 内，属于"事后补写"：结构合法，但不是宿主原生写入路径，靠 `step/end` 关掉工具生命周期。
