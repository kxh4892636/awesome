# 004-两包校验规则是否同源

## 问题

`repos/pi-toolkit` 与 `repos/dsh-toolkit` 各带一份领域文档校验脚本。改一条规则时不确定改一处还是两处；两边入口行长不一样（17.8 KB vs 20.4 KB），看着像已经分叉。

## 答案

规则同源：`lib/checks.mjs`、`lib/render.mjs`、`lib/pacing.mjs` 逐字相同，`lib/fix.mjs` 只差模块注释里的包名。入口长度不同是因为「壳」不同——pi 在工具内进程 import 后直接跑；dsh 走子进程 JSON 契约、保留 CLI，输出多一个 `fixed` 字段。

所以：**改规则改 `lib/`，两包同步；只改入口壳时不必。**

新增一个 `lib/` 模块是例外：判定逻辑同源，接线却在入口——`pacing.mjs` 的取脏路径与「只对 `active` Plan 调判定」由 `check-domain.mjs` 各接一次，只同步 `lib/` 不会生效。

> 纠正（2026-11-19，来源 `repos/*/lib/base.mjs` 实读 + dsh 提交 `83ba8dd`）：`lib/base.mjs` 不再是逐字一致。两包的**默认上限**按宿主不同——pi `noteDescriptionMaxChars: 233`、`guideMaxBytes: 13 KB`；dsh `144`、`21 KB`（dsh 有意为之，见 `src/contract.ts` 的 `DEFAULT_NANO_FLOW_SETTINGS`）。规则逻辑仍同源，只有这两行默认值分叉。
>
> 本工作区的 `$DSH_HOME/toolkit/nano-flow.json` 把 `noteDescriptionMaxChars` 写成 233、`guideMaxBytes` 写成 13312，所以**运行时以面板设置为准（233 字 / 13 KB），与代码默认值不同**；GUIDE 里写死的上限数字因此不可靠，读每轮注入的「篇幅限制」块。

## 验证

```bash
for f in base checks render fix pacing; do
  diff -q repos/pi-toolkit/src/nano-flow/scripts/lib/$f.mjs \
          repos/dsh-toolkit/src/nano-flow/documents/lib/$f.mjs
done
```

`checks` / `render` / `pacing` 应无输出；`fix` 差一行模块注释；`base` 只应差 `noteDescriptionMaxChars` 与 `guideMaxBytes` 两行默认值——差出别的行就是规则真分叉。dsh 侧另有 `base.d.mts` / `pacing.d.mts`（给测试 import 的类型声明），pi 没有，比对只看 `.mjs`。跨包改动后两包各跑一次 `check-domain.mjs <repo>`，同一份 fixture 的输出应当一致。
